# The Four Properties

Source: Doherty Threshold (IBM, 1982 — ~400 ms) and Nielsen's response-time envelope (0.1 s / 1 s / 10 s). Chat AI lives in the 10 s+ range; agentic AI lives in minutes-to-hours. Most products surface only two states — "thinking" and "done" — which forces users to invent rituals (tab-checking, reloading, pinging the model, screen recorders). The fix is not new technology. It is applying 40 years of long-running-operation conventions to AI agents.

Every code path generated by this skill must satisfy all four properties.

## 1. Continuous progress, not a pulsing dot

Show what the model is doing **right now**: which step, which tool call, which file.

**Implementation contract**
- Consume the `@anthropic-ai/claude-agent-sdk` streaming async iterator. Do **not** await the final response.
- Render each event type as it arrives:
  - `assistant` token deltas → append to the visible assistant bubble.
  - `tool_use` blocks → push a new row into a live tool-call list with state `running` and the input arguments captured.
  - `tool_result` blocks → transition the matching row to `complete` or `error`, store a truncated preview, link to the full result in the log.
  - Thinking/reasoning blocks → render collapsed and dimmed in the periphery ("calm computing", per Weiser).
- If percent-complete is unavailable, render an ordinal step counter ("Step 4 of ~12") and a live list of completed tool calls with timestamps.

**Failure modes this prevents**
- "Generating…" spinner with no underlying signal.
- Tool inputs visible in logs but invisible in UI.
- Long tool runs that look indistinguishable from a stall.

## 2. Time-remaining ETAs that update

A wrong-but-updating ETA beats no ETA. (Myers, 1985.)

**Implementation contract**
Derive the ETA from observable signals, recompute on **every** streamed event, and re-render:

- `avg_tool_duration` — rolling average of tool-call elapsed time within the current session.
- `token_throughput` — tokens/sec derived from the streaming endpoint over a moving window.
- `historical_task_duration` — median duration by task type (if classification exists), persisted across sessions.

Expose both elapsed time and a refining estimate. Neither must ever freeze. If signals are insufficient (cold session, no history), show only elapsed and label the ETA as "warming up".

**Failure modes this prevents**
- ETA computed once at start and never updated.
- ETA hidden when uncertain — show the elapsed counter at minimum.

## 3. OS-level completion notifications

Do not require the user to babysit a tab.

**Implementation contract**
When the SDK stream terminates (final `message_stop` or equivalent end-of-turn signal), fire a notification:

- Browser contexts → Web Notifications API. Request permission once at app start, not on first fire. Notifications include task title, outcome (`success` / `error` / `aborted`), and a deep link back to the session.
- Native/Electron contexts → platform notification channel (`node-notifier`, macOS `UNUserNotification`, Windows toast, Linux `libnotify`).
- Idle-gap heartbeat — if no event arrives for >60 s, fire a "still running" notification so the user can distinguish a stalled connection from a healthy long step.

**Failure modes this prevents**
- Logic gated on `document.hasFocus()` (defeats the whole point).
- Fire-on-every-event spam — only terminal transitions and idle heartbeats.
- Notifications without a deep link — the user has to hunt for the session.

## 4. A persistent, readable log

Every long operation must leave an auditable trail accessible during **and** after the run. This is what eliminates the screen-recorder workaround.

**Implementation contract**
Persist each streamed event to durable storage. Each record carries:

| Field | Notes |
|-------|-------|
| `timestamp` | ISO 8601 with ms |
| `sessionId` | UUID, stable across the run |
| `eventType` | The normalized `AgentEvent` type |
| `toolName` | If applicable |
| `toolInput` | Full input, not truncated in storage |
| `toolResultSummary` | First N chars + full result location reference |
| `tokenCounts` | Cumulative input/output |
| `modelId` | The exact model string |

Storage adapters:
- `JsonlLogSink` (Node) — append-only JSONL, one file per session under `{{LOG_DIR}}`.
- `IndexedDbLogSink` (browser) — `agent-events` database, object store per session.

The log surfaces in a scrollable UI that updates live (tail-style) and remains queryable indefinitely.

**Failure modes this prevents**
- Intermediate tool outputs discarded when the next step starts.
- UI truncation cascading into storage truncation.
- Reducers that read directly from the SDK shape (replay impossible).

## Cross-cutting non-negotiables

- **Single event source.** UI, ETA, notifications, and log all derive from the same normalized `AgentEvent` stream. Never branch UI logic off the raw SDK shape.
- **Event-sourced replay.** Replaying the persisted log must reproduce reducer state exactly.
- **Animation-frame throttle for UI only.** Never throttle log writes. Every event persists.
- **Heartbeat the connection.** Distinguish "model is thinking" from "the connection died" — show the timestamp of the last event during long gaps.
